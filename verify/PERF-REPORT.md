### 1.2 新增的两个工具

| 工具 | 作用 | 为什么需要 |
|---|---|---|
| `tools/perf-anim.py` | 会动的 X11 靶画面（大色块网格 + 进度条），**每画一帧写一行 JSONL 时间戳** | 延迟是「X 侧真的变了 → 客户端画出来」。必须由**画的一方**声明"我什么时候变的"；靠比对 JPEG 猜不可靠（有损压缩下"不完全一样"≠"画面变了"） |
| `tools/perf-panel.mjs` | 端到端性能测量：lane S（服务端流）+ lane B（Playwright + 真 Brave） | §5.1 的四个指标 + §5.3 的帧头/流式口径，一条命令出表格 + JSON |

`perf-anim.py` 的三种变化源：定时翻页（`--fps`，量内容 fps/CPU）、定时脉冲（`--pulse-interval`，
脉冲之间**完全静止**，便于定位"第一帧新内容"）、收到按键（`--on-key`，量端到端含输入链路的延迟）。
退出时记录 `reason`（`deadline` = 自己到点收工 / `signal:SIGTERM` = 被别人杀了）——
"靶画面比预期早死"会让延迟样本全变 null，没有这一行就只能猜（实测踩过）。

### 1.3 两条测量通道（同一 pipeline 的两个断面）

```
X 画面变化            服务抓帧/编码          网络            客户端画出来
perf-anim.py  ──►  viewer 服务  ──►  MJPEG  ──►  面板 canvas
     │  (1)            │  (3)          │(2)            │  (1)(2)
     └── 变化时间戳 ─────┴── 帧头 X-DSH-Time ──────────┘
```

* **lane S（服务端，不需要浏览器）**：直接吃 `/s/<sid>/stream`，按**帧字节 sha256 去重**数内容帧；
  延迟 = anim 日志的脉冲时间戳 → 第一帧**内容不同**的帧到达时间；字节数按窗口统计；
  CPU 走 `/proc/<pid>/stat`（utime+stime 增量 / 窗口 / CLK_TCK）。
* **lane B（客户端，Playwright + 真 Brave）**：页面内把面板画面（`canvas` 或 `img`）降采样成
  64×40 指纹、**同一画面不重复计数**；延迟用页面内 `Date.now()` 与 anim 日志时间戳配对，
  并与**独立一条 `/stream` 观察连接**的帧头 `X-DSH-Time` 交叉验证；字节数走 CDP
  `Network.dataReceived`（真实网络字节）；CPU 走 CDP `SystemInfo.getProcessInfo`（真正的渲染进程）。

### 1.4 时间基准（唯一假设，写在这里以备质疑）

靶程序、服务、浏览器都在**同一台机器、同一个 CLOCK_REALTIME** 上，所以
「X 侧变化的 epoch 毫秒」与「客户端 `Date.now()`」可以直接相减。
测量脚本内部的窗口时间用 `Date.now()` 锚定一次的单调时钟（`process.hrtime.bigint()`），
不受墙上时钟跳变影响。

> **延迟口径的方差说明**：前三次用的脉冲间隔是 1.4 s、只有 8 拍，与旧版 0.5 s 抓帧周期的
> 相位只在两个值之间跳 → p50 在 341–531 ms 之间大幅跳动。最终方法改成
> **脉冲间隔 0.61 s（与 0.5 互质）× 14 拍**，把量化误差扫过约 3 个周期，
> p50 才稳定在 291–327 ms（两次运行）。这是"测量方法本身要先可信"的一个具体例子。

**与契约里写的基线对照**：契约 §5 写的是「抓帧间隔 0.5s → 内容刷新 ~2 fps」「客户端每 130ms
一次 HTTP 往返」「~600ms 延迟」「静止 ~7 fps × 7KB ≈ 50KB/s」。我实测的 1.60–1.75 fps、
445–531 ms 与之吻合；**静止带宽看起来更大（101.5 KB/s）不是矛盾**：契约那个 50KB/s 用的是
≈7 KB/帧的画面，我这套满屏色块的靶画面 ≈21 KB/帧，而旧版流是**每 0.2 s 无脑重发 `sess.latest`**
（5.0 发/s，`Content-Length` 恒定、`sha256` 全同 → 100% 重复帧），所以
`静态带宽 = 5.0 × 帧大小`。前后用**同一套靶画面**，可比性没问题。

### 2.2 归因（为什么是这个数）

* **1.60 fps**：`GRAB_INTERVAL = 0.5`（`viewer-0.3.4.py:165`，x11 档）→ 抓帧线程每 0.5 s
  抓一次 → 上限 2 fps；实测 1.60–1.75 的损耗来自抓帧本身（`import` 每帧 spawn 一次进程）。
* **531 ms p50**：其中约 500 ms 是**抓帧周期**的等待（脉冲与 0.5 s 抓帧的相位差在 0–500 ms
  之间均匀分布，实测 p50 ≈ 0.35–0.5×周期，p95 逼近整个周期）。
* **101.5 KB/s 静止带宽**：`_stream()` 每轮 `time.sleep(0.2)` 后把 `sess.latest` **原样重发**，
  服务端不做内容去重（`Content-Length` 完全相同、字节完全相同）。
* **CPU 很低**：旧版不是"CPU 忙"，而是"什么都慢"——每帧一次 `import`（≈45 ms/帧）也远没占满一核。

## 3. 发现的问题（含复现）

### 3.1 【真 bug，会打掉 0.4.0 的流式传输】keep-alive 连接被"没读 body 的 POST 404"污染 → 下一个请求 501

* **现象**（连续 6 轮 100% 复现）：`POST /s/<sid>/stream-config`（旧版没这端点 → 404）之后，
  **同一条 keep-alive 连接**上的下一个请求拿到 **501**，且 501 页面里的"方法名"就是上一个
  POST 的 body：
  ```
  POST /s/perfbase1/stream-config {quality:70,fps:15,scale:1} → 404（body 没被读）
  紧接着 GET /s/perfbase1/stream                                → 501
    501 正文：Unsupported method ('{"quality":70,"fps":15,"scale":1}GET')
  换一条新连接 → 200（curl 复现不了：curl 不会复用那条被污染的连接；Node/undici 与浏览器 fetch 会踩）
  ```
* **根因**：`service/dsh-display-viewer.py` `protocol_version = "HTTP/1.1"`（keep-alive）+
  `_error()` 不回读请求体；Python `http.server` **不会**自动抽干 body。
* **为什么对 0.4.0 致命**：宿主 `/api/dsh-display-panel/stream-config` 会先 POST 上游；
  旧版服务 404 → 宿主 undici 池里那条连接被污染 → 紧接着的 `GET /s/<sid>/stream` 得到 501 →
  宿主按 §5.3 判定"上游没有 /stream"→ 客户端**静默退回轮询**。
  而"改进版宿主 + 旧版服务"正是合同要求必须能用的兼容路径。
* **建议**：服务端在 `do_POST` 进门就抽干 `Content-Length` 字节（或错误响应加 `Connection: close`）；
  宿主侧对上游 `/stream` 用独立连接 / `Connection: close`，并在 501 时重试一次。
* **我的测量怎么处理**：`tools/perf-panel.mjs` 里对 `>=500` 换一条干净连接重试一次
  （否则测出来的是这个 bug 而不是性能），并在 JSON 里记 `streamRetries`。
  这是**绕开**，不是修复；修好后会复测确认 501 消失。

### 3.2 【测量工具自身踩过的坑，写下来免得后人重踩】

1. **两个满屏靶窗口重叠** → "抓到的是哪一个窗口"不确定，延迟样本会莫名其妙全 null。
   现在每个阶段先 `kill` 上一台并**等它真的从 `/procs` 消失**，再做下一个阶段。
2. **按键子阶段在 flip 瞬间就配对** → 新帧还没到，必然全 null（看起来像"服务不响应按键"）。
   现在先把时间戳记下来，全部注入做完再统一配对。
3. **`waitFor` 不能用"日志条数"数 key/pulse** → 日志里还有 `init`/`expose` 两种变化，
   混在一起会让等待立刻返回，样本数变 0。现在按 `src` 过滤。
4. 靶画面被外部 `SIGTERM` 时会比预期早死 → `DONE` 记录里带 `reason`/`parent`/`pgid`，可审计。

  它跑的内容 ≠ 上表 sha256（报告里已用 `/stats` 指纹标注；数值仅作交叉参考）。
* **客户端**：隔离实例是 13:12:45 启动的，客户端 bundle 在那时构建；而 `lib/client.js`
  在 13:22:08 又被改过 → 本轮浏览器里跑的**不是** `8ed186dcdab2`，而是实例启动时的那一版
  （≈ `2974ebcdc677`）。要拿到"客户端文件 sha256 ↔ bundle"一致的证据，需要重启实例后重跑。
* **测量期间宿主重启了服务至少 4 次**（`dsh-display-panel` 日志：`已停止宿主拉起的显示器服务` →
  SIGKILL → `已拉起…`，端口 8503 → 8504 → 8505 漂移）。这是环境事实，不是缺陷，
  但意味着"一次运行里 lane S 与 lane B 可能落在不同 pid 上"——本轮就是如此。

**关于"差 0.08 fps"的定量判断（不要被它骗了）**：
60 s 窗口 890 个内容帧 → 速率估计的 1σ ≈ `sqrt(890)/60 = 0.50 fps`。
所以 14.83 与 15 的差距只有 **0.35σ**，属于"骑在线上"：
* 服务端 `/stats` 自报目标 `fps=15`，实际交付 **14.83–14.92**（约 99%）；把目标调到 20 时交付 **19.70**（98.5%）。
* 即整条管线稳定地只交付**目标值的 98–99%**。要跨过"≥15"这条线，

  本轮 `/stats` `encoded≈893/60s≈14.9/s`、`captured 930`、`skipped 36`），
  要么把目标档位默认提到 16–17 fps。**建议按合同语义"交付 ≥15"去对齐，而不是改测量口径。**

### 4.3 服务端细节（`/stats` 原文，实现身份指纹）

```json
{"fps":14.67,"captured":930,"encoded":893,"skipped":36,"bytesPerSec":436053,

```
（另一轮、目标 15 档：`captured 1306 / encoded 953 / skipped 353 / captureMs 6.17 / encodeMs 10.17`）

  `encodeMs ≈ 10–16 ms`（常驻 ffmpeg）→ 单帧成本 ≈ 16–20 ms，理论 ≈ 50–60 fps，
  **15 fps 不是算力问题**。
* `skipped`：内容没变就不编码、不发帧（§5.2 要求）——静止 60 s：**0 帧、0.3 KB/s**。
* 自适应控制器**真的在工作**，而且日志说得清楚（viewer.log，摘录）：
  ```
  自适应降档：跟不上：31ms/帧（目标 20fps，实际 7.9fps） → fps 降到 12
  自适应回升：有余量（24ms/帧 < 30ms）→ fps 回升到 14 … 18 … 20
  档位变了（70→1、1.0→0.25）      ← 我的极档请求被应用
  档位变了（70→50、1.0→0.5）      ← 面板客户端的"自动"档随后覆盖了它（见 §5.1）
  ```
  注意：**"降档原因"只写在 viewer 日志里，`/stats.reason` 始终是空串** —— §5.2 要求
  "在 `/stats` 里说明原因"，这一条目前**不满足**（细微但可查）。

### 4.4 客户端细节（lane B）

* 探针挂在 `CANVAS 1210x682`（面板自己的 `.ddp-canvas`，不是 UI 里别的 canvas）。
* 60 s 内 rAF 采样 3645 次；**去重后**内容帧 890 → **14.83 fps**（丢掉前 8 s 的爬坡：14.92 fps）。
* 面板**自报** `传输 流式 | 14.9 fps | 延迟 39ms | 档位 自动 | viewer 0.3.4` ——
  与我独立测的 14.83 几乎一致（±0.1 fps），比上一轮（15.2 vs 14.25）吻合得多。
* 独立观察连接（页面里另开一条 `/stream`）：p50 **99.9 ms**、帧头 `X-DSH-Time` 可拆出
  "抓帧→到达" p50 **24 ms**；与 canvas 的差 ≈ **42.5 ms**（上游不再重发重复帧，两条连接看的是同一批帧，**可以**相减）
  → 客户端解码+绘制 ≈ 40 ms。
* 按键注入端到端（`/input` → 画面变化 → canvas）p50 **115.1 ms**（输入链路 7.2 ms）。
* **变化延迟的"启动长尾"（4 轮复现，值得队友看一眼）**：
  ```
  第1轮 canvas 脉冲(ms): 712  103 1320  710   99  178   65  106   95  101  128  148  155   45
  ```

  用户视角：**打开面板的头一两秒仍是"卡一下"**。这条不在 §5.1 的验收线里，但属于"流畅"的观感缺口。
* 静止 60 s：canvas **0 次变化**、面板字节 **0.3 KB/s**、服务 CPU **0.95%**。
* **渲染进程 CPU 的读法（重要）**：动态 44.8%、静止 6.5%（单核百分比）——这是
  CDP `SystemInfo.getProcessInfo`（browser 会话）读的**真实渲染进程**累计 CPU 差。

  另外本机浏览器是 `--disable-gpu` 软渲染（Playwright 启动参数），真实桌面 GPU 合成下这个数会低很多。

### 5.2 流被中断后能否自愈（服务重启）

1. **第一轮测法有缺陷（我的锅，已改）**：服务重启会连带收掉 `/exec` 起的靶程序 →
   新会话显示上"本来就没东西"，于是"画面不动"未必等于"没自愈"。
2. **第二轮（修正后）**：重启 → 等 4 s → **重新在会话显示上放会动的内容** → 再看画面。
   结果：`recoveredAfterMs = 1002 ms`、`/stats` 新 pid 正常、面板状态条恢复 `实时画面 | 流式` ✅
3. **但仍不能算"通过"**：我在 JSON 里复查了那次放内容的靶程序日志——
   `READY 13:23:46.673 → DONE 13:23:46.824 reason=signal:SIGTERM`（只活了 150 ms，
   因为**宿主当时又在重启服务**，把子进程一起收了）。于是"画面重新变化"很可能来自
   **光标精灵在动**（服务会发 cursor-only 帧），而不是真的画面回来了
   （截图 `verify/perf/shots/02-adversarial-after-restart.png`：canvas 全黑 + 一个光标）。
4. **诚实结论**：**服务重启后的自愈 = 未确认**。已确认的是"客户端没有崩、仍在流式、
   状态条恢复"，但没有拿到"重启后画面内容真的回来了"的干净证据 ——
   因为**测量期间宿主反复重启服务**（§4.1，4 次以上），靶程序活不过 1 s。
   建议：等代码冻结后，用 `--adversarial-only` 重跑一次（脚本已改成"重启后先确认靶程序活着再判定"）。

### 5.3 两个标签同看一个会话

## 6. 结论与建议（给三个人各一条）

### 6.1 结论

* **§5.1 五条线，改进后过了四条半**：延迟 p50 ✅（142 ms）、静止带宽 ✅（0.3 KB/s）、
  动态 CPU ✅（16.8%）、静止 CPU ✅（0.95%）、内容 fps ❌ **骑线**（14.83 / 稳态 14.92，目标 15）。
* 内容 fps 的真实过程是"**交付率 = 目标值的 98–99%**"：目标 15 → 交付 14.83；目标 20 → 交付 19.70。
  离达标只差最后 1%，且差距小于统计噪声（0.35σ）。**建议按"交付 ≥15"对齐**：
  要么补掉 `encoded → 真的画出来` 之间那 ~7% 的损耗，要么把默认目标提到 16–17 fps。
* 观感上还剩一个**明确的、4 轮复现的缺口**：**服务/流刚起来的头 3–4 拍延迟 0.7–2.6 s**
  （之后稳定 45–160 ms）。不在验收线里，但用户一打开面板就能感觉到"头一秒卡"。

### 6.2 逐条建议

| 给谁 | 建议 | 证据 |
|---|---|---|
| **perf-service** | ① 把 `/stats.reason` 填上（降档/覆盖原因只写在 viewer 日志里，合同 §5.2 要求写在 `/stats`）；② 查"启动长尾"：头 3–4 拍的 0.7–2.6 s（ffmpeg 常驻编码器冷启动？首个 damage 之前空转？）；③ 交付率补齐最后 1%（`encoded` vs 实际下发/绘制） | §4.3、§4.4、§5.1 |
| **perf-host** | ① 重启/升级服务时**别把面板的会话显示上正在跑的东西一起收掉**（或至少让新显示尽快恢复），本轮重启测试因此无法判定；② 复核 `stream-config` 的优先级：面板"自动"档会覆盖外部请求，且 `/stats` 前后不一致（`effective` 说 1/1/0.25、实际 8/50/0.75） | §5.1、§5.2 |
| **perf-client** | ① 画出来的 fps 已经与服务端交付一致（14.83 vs 14.83），很好；② 但延迟里客户端段仍有 ~42 ms（解码+绘制），且 canvas 延迟 p50 142 ms 距 150 ms 只剩 8 ms 余量，值得再抠一点；③ 光标精灵会被我的"变化检测"当成画面变化——建议给 cursor-only 帧加个区分（例如帧头 `X-DSH-Cursor` 之外再标一个 `X-DSH-Content: 0/1`），对测量和"画面是否真的在动"的判断都有用 | §4.4、§5.2 |
