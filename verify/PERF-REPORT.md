### 1.2 新增的两个工具

| 工具 | 作用 | 为什么需要 |
|---|---|---|
| `tools/perf-anim.py` | 会动的 X11 靶画面（大色块网格 + 进度条），**每画一帧写一行 JSONL 时间戳** | 延迟是「X 侧真的变了 → 客户端画出来」。必须由**画的一方**声明"我什么时候变的"；靠比对 JPEG 猜不可靠（有损压缩下"不完全一样"≠"画面变了"） |
| `tools/perf-panel.mjs` | 端到端性能测量：lane S（服务端流）+ lane B（Playwright + 真 Brave） | §5.1 的四个指标 + §5.3 的帧头/流式口径，一条命令出表格 + JSON |

`perf-anim.py` 的三种变化源：定时翻页（`--fps`，量内容 fps/CPU）、定时脉冲（`--pulse-interval`，
脉冲之间**完全静止**，便于定位"第一帧新内容"）、收到按键（`--on-key`，量端到端含输入链路的延迟）。
退出时记录 `reason`（`deadline` = 自己到点收工 / `signal:SIGTERM` = 被别人杀了）——
"靶画面比预期早死"会让延迟样本全变 null，没有这一行就只能猜（实测踩过）。

### 1.3 两条测量通道（同一 pipeline 的两个断面）

```
X 画面变化            服务抓帧/编码          网络            客户端画出来
perf-anim.py  ──►  viewer 服务  ──►  MJPEG  ──►  面板 canvas
     │  (1)            │  (3)          │(2)            │  (1)(2)
     └── 变化时间戳 ─────┴── 帧头 X-DSH-Time ──────────┘
```

* **lane S（服务端，不需要浏览器）**：直接吃 `/s/<sid>/stream`，按**帧字节 sha256 去重**数内容帧；
  延迟 = anim 日志的脉冲时间戳 → 第一帧**内容不同**的帧到达时间；字节数按窗口统计；
  CPU 走 `/proc/<pid>/stat`（utime+stime 增量 / 窗口 / CLK_TCK）。
* **lane B（客户端，Playwright + 真 Brave）**：页面内把面板画面（`canvas` 或 `img`）降采样成
  64×40 指纹、**同一画面不重复计数**；延迟用页面内 `Date.now()` 与 anim 日志时间戳配对，
  并与**独立一条 `/stream` 观察连接**的帧头 `X-DSH-Time` 交叉验证；字节数走 CDP
  `Network.dataReceived`（真实网络字节）；CPU 走 CDP `SystemInfo.getProcessInfo`（真正的渲染进程）。

### 1.4 时间基准（唯一假设，写在这里以备质疑）

靶程序、服务、浏览器都在**同一台机器、同一个 CLOCK_REALTIME** 上，所以
「X 侧变化的 epoch 毫秒」与「客户端 `Date.now()`」可以直接相减。
测量脚本内部的窗口时间用 `Date.now()` 锚定一次的单调时钟（`process.hrtime.bigint()`），
不受墙上时钟跳变影响。

### 1.5 基线复现命令（一条）

```bash
cd /home/xgl/python/DSH插件/dsh-display-panel
# 脚本自己起冻结基线服务（8504）+ 靶程序，跑完自己收尸；不碰用户实例，也不碰队友的端口
```

## 2. 基线（0.3.4 冻结版）实测

### 2.1 数字

**环境**：Xvfb 1600×1000×24，8 核；靶画面 20 fps（远超目标 15 fps，保证瓶颈在管线而不是画面源），
满屏色块 ≈ 21 KB/帧。同一口径也复现过两次（见 §2.3 原始输出）。

| 指标 | 基线实测 | §5.1 目标 | 差多少 | 判定 |
|---|---|---|---|---|
| 内容 fps（帧字节去重） | **1.60**（另一次 1.75） | ≥ 15 | 差 **13.4** | ❌ |
| 变化延迟 p50 | **531 ms**（另一次 445 ms） | ≤ 150 ms | 超 **381 ms** | ❌ |
| 变化延迟 p95 | **742 ms**（另一次 549 ms） | —（p50 是验收线） | — | 记录 |
| 静止画面带宽 | **101.5 KB/s** | ≤ 5 KB/s | 超 **96.6 KB/s** | ❌ |
| 动态画面带宽 | 105.6 KB/s（5.0 发/s × 21.1 KB） | —（静止才是验收线） | — | 记录 |
| 服务单核 CPU（动态） | **0.25%** | ≤ 25% | 达标 | ✅ |
| 服务单核 CPU（静止） | **0.35%** | ≤ 2% | 达标 | ✅ |
| 按键注入延迟（`POST /input` → 画面变化 → 帧到达） | p50 **441 ms**（其中输入链路 3.5 ms） | —（同一 p50 线的另一条路径） | — | 记录 |
| Xvfb CPU（动态/静止） | 2.10% / 0.60% | —（仅供参考） | — | 记录 |
| 靶程序 CPU（动态） | 0.90% | —（测量开销，需可见） | — | 记录 |

**与契约里写的基线对照**：契约 §5 写的是「抓帧间隔 0.5s → 内容刷新 ~2 fps」「客户端每 130ms
一次 HTTP 往返」「~600ms 延迟」「静止 ~7 fps × 7KB ≈ 50KB/s」。我实测的 1.60–1.75 fps、
445–531 ms 与之吻合；**静止带宽看起来更大（101.5 KB/s）不是矛盾**：契约那个 50KB/s 用的是
≈7 KB/帧的画面，我这套满屏色块的靶画面 ≈21 KB/帧，而旧版流是**每 0.2 s 无脑重发 `sess.latest`**
（5.0 发/s，`Content-Length` 恒定、`sha256` 全同 → 100% 重复帧），所以
`静态带宽 = 5.0 × 帧大小`。前后用**同一套靶画面**，可比性没问题。

### 2.2 归因（为什么是这个数）

* **1.60 fps**：`GRAB_INTERVAL = 0.5`（`viewer-0.3.4.py:165`，x11 档）→ 抓帧线程每 0.5 s
  抓一次 → 上限 2 fps；实测 1.60–1.75 的损耗来自抓帧本身（`import` 每帧 spawn 一次进程）。
* **531 ms p50**：其中约 500 ms 是**抓帧周期**的等待（脉冲与 0.5 s 抓帧的相位差在 0–500 ms
  之间均匀分布，实测 p50 ≈ 0.35–0.5×周期，p95 逼近整个周期）。
* **101.5 KB/s 静止带宽**：`_stream()` 每轮 `time.sleep(0.2)` 后把 `sess.latest` **原样重发**，
  服务端不做内容去重（`Content-Length` 完全相同、字节完全相同）。
* **CPU 很低**：旧版不是"CPU 忙"，而是"什么都慢"——每帧一次 `import`（≈45 ms/帧）也远没占满一核。

## 3. 发现的问题（含复现）

### 3.1 【真 bug，会打掉 0.4.0 的流式传输】keep-alive 连接被"没读 body 的 POST 404"污染 → 下一个请求 501

* **现象**（连续 6 轮 100% 复现）：`POST /s/<sid>/stream-config`（旧版没这端点 → 404）之后，
  **同一条 keep-alive 连接**上的下一个请求拿到 **501**，且 501 页面里的"方法名"就是上一个
  POST 的 body：
  ```
  POST /s/perfbase1/stream-config {quality:70,fps:15,scale:1} → 404（body 没被读）
  紧接着 GET /s/perfbase1/stream                                → 501
    501 正文：Unsupported method ('{"quality":70,"fps":15,"scale":1}GET')
  换一条新连接 → 200（curl 复现不了：curl 不会复用那条被污染的连接；Node/undici 与浏览器 fetch 会踩）
  ```
* **根因**：`service/dsh-display-viewer.py` `protocol_version = "HTTP/1.1"`（keep-alive）+
  `_error()` 不回读请求体；Python `http.server` **不会**自动抽干 body。
* **为什么对 0.4.0 致命**：宿主 `/api/dsh-display-panel/stream-config` 会先 POST 上游；
  旧版服务 404 → 宿主 undici 池里那条连接被污染 → 紧接着的 `GET /s/<sid>/stream` 得到 501 →
  宿主按 §5.3 判定"上游没有 /stream"→ 客户端**静默退回轮询**。
  而"改进版宿主 + 旧版服务"正是合同要求必须能用的兼容路径。
* **建议**：服务端在 `do_POST` 进门就抽干 `Content-Length` 字节（或错误响应加 `Connection: close`）；
  宿主侧对上游 `/stream` 用独立连接 / `Connection: close`，并在 501 时重试一次。
* **我的测量怎么处理**：`tools/perf-panel.mjs` 里对 `>=500` 换一条干净连接重试一次
  （否则测出来的是这个 bug 而不是性能），并在 JSON 里记 `streamRetries`。
  这是**绕开**，不是修复；修好后会复测确认 501 消失。

### 3.2 【测量工具自身踩过的坑，写下来免得后人重踩】

1. **两个满屏靶窗口重叠** → "抓到的是哪一个窗口"不确定，延迟样本会莫名其妙全 null。
   现在每个阶段先 `kill` 上一台并**等它真的从 `/procs` 消失**，再做下一个阶段。
2. **按键子阶段在 flip 瞬间就配对** → 新帧还没到，必然全 null（看起来像"服务不响应按键"）。
   现在先把时间戳记下来，全部注入做完再统一配对。
3. **`waitFor` 不能用"日志条数"数 key/pulse** → 日志里还有 `init`/`expose` 两种变化，
   混在一起会让等待立刻返回，样本数变 0。现在按 `src` 过滤。
4. 靶画面被外部 `SIGTERM` 时会比预期早死 → `DONE` 记录里带 `reason`/`parent`/`pgid`，可审计。
